## 1. 背景

军棋（陆战棋）是国内认知度极高的传统棋类，但安卓应用市场上的现有产品普遍存在三个问题：
广告插屏频繁、强制登录与联网、规则实现不一致（尤其是铁路走法、行营保护、碰雷判定各家不同）。
很多玩家只想要"打开就能下一盘、规则正统、不联网"的产品。

前身版本 `junqi-android` 已在一次性开发中验证了技术路径（HTML5 Canvas + Capacitor 可行），
但存在两个结构性问题：规则定义散落在代码里无法追溯；AI 为演示性贪心，可玩性不足。
本项目为**重构版**，采用文档先行 + 迭代推进，先把规则和验收标准定义清楚，再写代码。

## 2. 目标与非目标

### 2.1 目标
| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G-1 | 规则正统且可追溯 | 规则说明文档覆盖全部判定分支，引擎单测 100% 覆盖吃子表与走法分支 |
| G-2 | 两种玩法完整可玩 | 翻棋、背靠背暗棋均可完成人机与热座整局对局，无卡死无异常 |
| G-3 | 纯离线零打扰 | 无网络权限、无广告、无账号，APK 体积 < 15 MB |
| G-4 | AI 有基本棋力 | 迭代 3 后 AI 对随机走子胜率 > 90%，人机对局玩家不会觉得"AI 在送子" |
| G-5 | 手机端体验合格 | 主流机型竖屏适配，一局启动到落子 < 3 秒，无明显掉帧 |

### 2.2 非目标（本项目明确不做）
- 联机对战、排行榜、账号系统（迭代 6 之后再评估）
- 四国军棋（4 人玩法）
- 内购、广告、数据上传
- iOS 版本

## 3. 目标用户与场景

| 用户画像 | 特征 | 核心诉求 | 典型场景 |
| --- | --- | --- | --- |
| U1 怀旧玩家（30–55 岁） | 小时候玩过实体军棋 | 规则要正统，操作要简单 | 通勤、午休单人打一局 |
| U2 休闲玩家（18–35 岁） | 喜欢轻度策略，怕规则复杂 | 上手快、有运气成分 | 排队等人时玩翻棋 |
| U3 双人同屏玩家 | 和朋友/孩子面对面玩 | 一台手机两个人能玩 | 家里、聚会、亲子 |

**核心痛点**：现有产品广告多、要联网、规则不一致；实体棋子需要第三人当裁判，凑不齐人就玩不了暗棋。
本产品用系统充当裁判，解决"两个人也能下正统暗棋"。

## 6. 需求描述（EARS）

采用 EARS 句式，保证每条需求可测。前缀含义：`U` 恒定约束、`E` 事件驱动、`X` 异常处理、`S` 状态驱动、`O` 可选功能。

### 6.1 恒定约束（Ubiquitous）
- **R-U-01** 系统应始终以 12 行 × 5 列棋盘、每方 25 枚棋子进行对局。
- **R-U-02** 系统应始终保证规则引擎不依赖任何 DOM 或渲染接口，可在 Node 环境独立运行。
- **R-U-03** 系统应始终对当前行动方仅暴露其有权知晓的信息（己方棋子、已揭示棋子、公共战斗结果）。
- **R-U-04** 系统应始终禁止地雷与军旗主动移动。
- **R-U-05** 系统应始终保证行营内的棋子不被攻击。
- **R-U-06** 系统应始终在无网络权限的前提下运行全部功能。
- **R-U-07** 系统应始终以 `docs/规则说明.md` 定义的吃子判定表结算战斗。

### 6.2 事件驱动（Event-driven）
- **R-E-01** 当玩家在首页选择玩法与对手后，系统应进入对应的开局流程（翻棋 → 直接开局；暗棋 → 布阵页）。
- **R-E-02** 当玩家点击一枚己方可移动棋子时，系统应高亮该棋子并显示其全部合法落点。
- **R-E-03** 当玩家点击一个合法落点时，系统应执行移动、结算战斗、切换行动方，并标记上一手起终点。
- **R-E-04** 当玩家在翻棋中点击一枚背面棋子时，系统应揭示该棋子的归属与军衔并结束本回合。
- **R-E-05** 当战斗发生时，系统应按当前 `revealMode` 公布结果，并在界面给出文字提示（如"我方连长 阵亡"）。
- **R-E-06** 当任一方司令阵亡时，系统应立即向双方揭示该方军旗位置。
- **R-E-07** 当一方军旗被吃时，系统应立即结束对局并展示结算弹层。
- **R-E-08** 当热座模式下一方回合结束时，系统应展示交接遮挡页，经确认后才显示下一方视野。
- **R-E-09** 当轮到 AI 行动时，系统应在 300–1200 ms 内给出走子（含"思考中"提示），且不得读取对手隐藏信息。
- **R-E-10** 当玩家在布阵页点击"随机布阵"时，系统应生成一个满足全部布阵约束的合法阵型。
- **R-E-11** 当玩家点击"开始对局"且阵型合法时，系统应进入对局阶段。
- **R-E-12** 当玩家退出应用时，系统应保存当前对局状态（F-09 生效后）。

### 6.3 异常处理（Unwanted）
- **R-X-01** 如果玩家点击非法落点，则系统应忽略该操作并保持当前选中状态，不改变对局状态。
- **R-X-02** 如果玩家的布阵违反任一布阵约束，则系统应阻止开始对局，并逐条列出违规项与所在位置。
- **R-X-03** 如果一方无任何合法行动，则系统应判该方失败并结束对局。
- **R-X-04** 如果达到无战斗步数上限，则系统应判和并结束对局。
- **R-X-05** 如果 AI 无合法走法，则系统应按 R-X-03 判负，不得抛出异常或卡死。
- **R-X-06** 如果存档数据版本不兼容或已损坏，则系统应丢弃存档并回到首页，同时提示"存档已失效"。
- **R-X-07** 如果玩家点击对手棋子或背面棋子（暗棋对局中），则系统应无响应，不泄露任何信息。
- **R-X-08** 如果玩家在 AI 思考期间操作棋盘，则系统应忽略该操作。

### 6.4 状态驱动（State-driven）
- **R-S-01** 在布阵阶段，系统应仅允许在本方 25 个可布格位上放置与调整棋子。
- **R-S-02** 在暗棋对局阶段，系统应将对手全部未揭示棋子渲染为背面。
- **R-S-03** 在翻棋对局阶段，系统应将背面棋子视为不可攻击、不可穿越的障碍。
- **R-S-04** 在 AI 思考期间，系统应禁用棋盘交互并显示等待态。
- **R-S-05** 在对局结束后，系统应禁用棋盘交互，仅保留"再来一局"与"返回首页"。
- **R-S-06** 在棋子进入大本营后（`hqLockIn = true`），系统应不再为该棋子生成任何走法。

### 6.5 可选功能（Optional）
- **R-O-01** 在开启悔棋功能处，系统应支持在人机对局中回退一个完整回合（玩家 + AI 应手）。
- **R-O-02** 在开启音效处，系统应在落子、战斗、胜负时播放对应音效。
- **R-O-03** 在开启阵型模板处，系统应支持保存、命名、载入与删除自定义阵型。
- **R-O-04** 在设置页开放规则开关处，系统应允许调整 `mineHitRule`、`revealMode`、`flipMoveMode` 并在新对局生效。

## 7. 核心流程

### 7.1 主流程
```
启动 → 首页（选玩法 / 选对手 / 难度）
        ├─ 翻棋   → 随机扣放 → 对局（翻子 or 走子）→ 结算
        └─ 暗棋   → 布阵（随机/手动 + 校验）→ [热座: 交接遮挡 → 对手布阵] → 对局 → 结算
结算 → 再来一局 / 返回首页
```

### 7.2 单回合流程
```
选中己方棋子 → 引擎生成合法落点 → 高亮
   ├─ 点空格   → 移动 → 换手
   ├─ 点敌子   → 战斗结算 → 揭示（按 revealMode）→ 判定胜负 → 换手
   └─ 点非法处 → 忽略（R-X-01）
翻棋额外分支：点背面子 → 揭示 → 换手（R-E-04）
换手 → 若下一方为 AI → 思考 → 走子；若为热座玩家 → 交接遮挡页
```

## 8. 交互说明

### 8.1 页面清单
| 页面 | 关键元素 | 备注 |
| --- | --- | --- |
| P1 首页 | 玩法选择（翻棋/暗棋）、对手选择（AI/双人）、难度、设置入口、续局入口 | 竖屏，单屏内完成 |
| P2 布阵页 | 棋盘、待布棋子槽、随机/清空/模板、校验提示、开始对局 | 仅暗棋 |
| P3 交接遮挡页 | "请交给对手，对手勿看"、确认按钮 | 仅热座 |
| P4 对局页 | Canvas 棋盘、双方剩余子力、当前行动方、上一手标记、战斗提示条、菜单（认输/悔棋/返回） | 主界面 |
| P5 结算弹层 | 胜负结果、用时、手数、再来一局/返回首页 | 覆盖 P4 |
| P6 设置页 | 规则开关、音效、动画开关、关于 | |

### 8.2 状态清单（对局页棋子视觉状态）
背面（未揭示）／己方明子（可选中）／己方明子（已选中，描边高亮）／敌方明子（可攻击时标红）／
合法落点（空格圆点提示）／上一手起点与终点（虚线框）／不可移动子（地雷、军旗、大本营锁定，灰度处理）／
行营内敌子（盾牌角标，表示不可攻击）。

### 8.3 交互边界
- 单指点击为唯一操作方式，不做拖拽（布阵页除外，迭代 4 增加拖拽）。
- 点击己方另一枚棋子 = 切换选中；点击已选中棋子 = 取消选中。
- 所有操作在 100 ms 内给出视觉反馈。
- 关键破坏性操作（认输、返回首页、清空布阵）必须二次确认。

## 9. 数据指标与埋点

**本产品不上传任何数据**，所有指标仅落本地存储，用于战绩页与自测；埋点表在此定义以保证后续如接入分析可直接复用。

| 事件 | 关键字段 | 用途 |
| --- | --- | --- |
| `game_start` | mode, opponent, aiLevel, rules | 玩法偏好分布 |
| `game_end` | mode, result, moves, durationSec, endReason | 完成率、平均时长、和棋比例 |
| `layout_done` | isRandom, durationSec, retryCount | 布阵易用性（手动布阵放弃率） |
| `illegal_tap` | phase, reason | 交互误操作热点 |
| `ai_move` | level, thinkMs, depth | AI 性能 |
| `crash` | stack, phase | 稳定性 |

**北极星指标**：单次启动完成整局对局的比例（目标 > 70%）。

## 10. 验收标准

### 10.1 通用（每个迭代都必须满足）
- AC-1 引擎单测全部通过；新增规则分支必须有对应用例。
- AC-2 两种玩法各跑通至少 1 局完整 AI 自动对局（无异常、无死循环）。
- AC-3 无控制台报错、无内存持续增长。
- AC-4 文档已同步：受影响的 PRD / 规则说明 / 架构文档 + `docs/迭代记录.md` 追加记录。

### 10.2 功能验收（示例，逐迭代细化到用例）
- AC-5 吃子判定表 12 种组合逐一验证正确。
- AC-6 工兵铁路转弯可达格位与手工推算一致；非工兵不得转弯。
- AC-7 行营内棋子无法被吃；行营斜线走法可用。
- AC-8 布阵违规（军旗不在大本营 / 地雷越排 / 炸弹在第一排 / 行营有子）均被拦截并给出定位提示。
- AC-9 暗棋对局中，通过界面无法获知对手任何未揭示棋子的军衔（含 DOM/存档层面不泄露）。
- AC-10 翻棋中背面棋子不可被吃、不可被铁路穿越。
- AC-11 结算触发条件正确：夺旗、无合法行动、和棋三种均可复现。

### 10.3 发布验收（迭代 6）
- AC-12 签名 APK 可在 Android 8.0+ 真机安装并完成两种玩法各一局。
- AC-13 APK 体积 < 15 MB，无网络权限申报。
- AC-14 冷启动到首页 < 2 秒。

## 11. 边界与异常场景清单

| 场景 | 期望行为 |
| --- | --- |
| 双方均只剩不可移动棋子（地雷/军旗） | 判和（R-X-04 兜底） |
| 一方仅剩军旗与地雷，另一方无工兵与炸弹 | 允许继续，直至步数上限判和 |
| 翻棋开局连续翻到对手棋子 | 正常揭示，归属为对手，不影响回合切换 |
| 暗棋一方大本营放非军旗棋子被吃 | 正常结算，不触发胜负 |
| 铁路长驱路径上有背面棋子（翻棋） | 视为阻挡，走法非法 |
| 应用被系统杀死 | 下次启动可续局（F-09 后）；此前回到首页 |
| 横屏 / 折叠屏 / 刻痕屏 | 锁定竖屏，安全区内布局，不遮挡棋盘 |
| 系统字体放大 | 关键按钮不被截断 |
